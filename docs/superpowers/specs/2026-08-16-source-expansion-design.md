## 무엇을 해결하는가

36명 모든 위인의 프론트매터 `sources`를 최소 10건으로 올린다. 현재 10건 미만인
31명에게 필요한 부족분은 합계 116건이다. 이 설계에서 1건은 단순 서지 레코드가 아니라
다음 네 산출물이 함께 있는 하나의 지식 단위다.

1. `sources.json`의 새 고유 행
2. `wiki/sources/<id>.md` 출처 페이지
3. 해당 위인 본문의 새롭고 근거 있는 주장
4. 위인 프론트매터와 각주 정의에 추가된 같은 출처 id

따라서 완료 상태의 레지스트리는 기존 142건과 새 116건을 합친 258건이고, 새 출처마다
서로 다른 주장 단위가 하나 이상 있어야 한다. 한 문장 끝에 새 각주 여러 개를 몰아 달아
여러 출처의 할당량을 동시에 채우지 않는다. 116건은 116개의 검증된 서지이면서 116개의
구분 가능한 근거 주장이다.

출처 수만 맞추면 되는 작업이 아니다. 가장 큰 위험은 **실재하는 문헌을 특정 위인과
무관한데도 관련 문헌처럼 등재하는 것**이다. Crossref가 제목·저자·DOI가 정확한 논문을
돌려줘도 그 논문이 가녜나 가녜의 이론을 다룬다는 뜻은 아니다. 그러므로 존재 검증과
관계 검증을 독립된 게이트로 둔다.

## 왜 넓히기를 먼저 하는가

출처가 4~9건인 31명은 질문에 답할 수 있는 실질 문헌의 폭이 좁다. 이 상태에서 몇 개
페이지의 특정 섹션만 깊게 파면 소수 위인의 답변은 좋아져도 전체 오라클의 공백은 남는다.
반대로 각 위인을 10건까지 올리려면 본인의 정초 저작, 후대의 직접 검토와 비판, 필요한 경우
공식 생애 기록을 골고루 찾게 된다. 그 과정이 낮은 출처 수와 취약한 단독 근거를 함께 드러낸다.

에드거 데일이 이 순서의 실측 근거다. 데일은 4건으로 하위 5명에 속하고 저장소 유일의
`confidence: low`다. 「기억률 피라미드는 데일의 것이 아니다」가 전문 백과사전 항목인
`molenda-2003-cone` tier C 하나에만 기대기 때문이다. 데일을 10건으로 보강하면서 원추,
세 판본, 기억률 피라미드 오귀속을 직접 다룬 문헌을 우선하면, 출처 폭을 늘리는 바로 그
작업이 이 C 단독 주장에 더 강한 근거를 붙인다. 보기 싫은 `low`를 없애려고 아무 A를
다는 것이 아니라, 가장 중요한 실질 질문의 문헌 공백을 메운 결과로 깊이가 따라온다.

반면 A 없는 33개 섹션을 0개로 만드는 것은 목표가 아니다. `ralph-tyler`의 「농촌 교사에서
교육평가 연구자로」 같은 생애·경력 서술은 대학 공식 기록이 올바른 근거이며 tier B가 천장인
것이 정상이다. 존재하지 않는 자서전을 찾거나 관련 없는 원저작을 생애 문단에 붙여
`high`를 만드는 것은 `CLAUDE.md`가 금지한 지표 역전이다.

## D1 — 세 단계 사이에 판정 권한을 섞지 않는다

확장은 후보 수집, 검증·등재, 본문 서술의 세 단계다. 같은 모델이 문헌을 찾고 스스로
실재·관계·티어를 승인한 뒤 그 문헌으로 글까지 쓰게 하지 않는다. 발견과 판정과 서술을
분리해야 한 단계의 환각이 다음 단계의 전제로 굳지 않는다.

| 단계 | 입력 | 출력 | 권한 |
|---|---|---|---|
| 1. 후보 수집 | 위인 식별 패킷, 현재 위인 페이지, 현재 id, 부족분 | 구조화된 후보 JSON | 저장소 read-only, 웹 검색 허용, stdout만 출력 |
| 2. 검증·등재 | 후보 JSON, 레지스트리·원문·서지 설명 | 승인 묶음, `sources.json` 행, source 페이지 | `curator`가 판단, 격리 worktree의 허용 파일만 쓰기 |
| 3. 본문 서술 | 현재 위인 페이지와 **그 위인에게 승인된 새 id만** | 수정된 위인 페이지와 출처별 주장 맵 | 생성기는 read-only·stdout, 오케스트레이터가 대상 파일 하나만 씀 |

메인 브랜치는 세 단계를 통과한 위인 커밋만 받는다. 단계 2 중간에는 새 source 페이지가
아직 위인 페이지에서 도달되지 않거나 confidence가 오래돼 strict lint가 실패할 수 있다.
이 빨간 중간 상태는 격리 worktree 안에만 있고 커밋하지 않는다. 메인의 초록은 유지한다.

### 1단계 — 후보 수집

한 위인의 부족분을 `n`이라 할 때 첫 수집은 `max(2n, n+3)`개 후보를 요청한다. n=1이면
4개, n=6이면 12개다. 탈락을 예상한 여유분이지 이 수만큼 등재하라는 뜻이 아니다. 검증 후
승인 수가 n보다 작으면 모자란 수에 대해 같은 공식을 다시 적용해 추가 수집한다.

수집 입력에는 다음만 넣는다.

- 위인 slug, 정규 이름, 생몰연도, 역할, 현재 페이지의 실질 섹션
- 현재 그 위인에게 선언된 출처 id와 서지
- 저장소 전체의 기존 id, 정규화한 제목·저자·연도, 영구 식별자 목록 — 중복 탐지용
- 부족분 n과 본인 원저작 우선순위
- 관계 유형과 후보 JSON 스키마

후보 하나는 최소한 다음 필드를 낸다.

```json
{
  "candidate_key": "collector-local-key",
  "bibliography": {
    "authors": ["표시 저자명"],
    "title": "원문 제목",
    "year": "발행연도 또는 판본 연도",
    "publisher": "저널·출판사·기관",
    "url": "발견 URL",
    "identifiers": {
      "doi": null,
      "isbn": null,
      "eric": null,
      "openlibrary_edition": null,
      "oclc": null
    }
  },
  "relation_proposal": {
    "kind": "authored_by",
    "person_role": "author",
    "matched_name": "문헌에 표시된 이름",
    "locator": "title page",
    "evidence_url": "관계 근거 URL",
    "evidence": "무엇이 관계를 보이는지의 짧은 설명"
  },
  "claim_seed": {
    "section": "들어갈 기존 또는 제안 섹션",
    "claim": "이 문헌으로 말할 수 있는 구체 주장",
    "locator": "쪽·절·초록 위치",
    "evidence_url": "주장 근거 URL"
  }
}
```

이 JSON의 `relation_proposal`은 후보 모델의 제안일 뿐 승인 기록이 아니다. 후보 모델은
최종 `tier`, `verified`, 최종 id를 정하지 않는다. 특히 Crossref 검색 결과를 받았다는
이유로 관계나 tier를 채우지 않는다.

후보 수집용 Codex 호출은 전역 설정을 믿지 않고 `-s read-only`를 명시한다. 이 저장소가
있는 환경의 `~/.codex/config.toml`에는 `sandbox_mode = "danger-full-access"`가 실제로
설정돼 있으므로 `-s` 생략은 읽기 전용 수집이 아니다. live 검색이 필요하면 `--search`도
명시한다.

설치된 `codex-cli 0.147.0`의 도움말과
[공식 non-interactive 문서](https://learn.chatgpt.com/docs/non-interactive-mode)는 진행 출력을
stderr로, 최종 메시지를 stdout으로 내보내는 계약과 `--output-schema`를 확인해 준다. 따라서
수집기는 다음 경계를 사용한다.

```bash
codex --search -a never -m gpt-5.6-luna exec \
  -s read-only --ephemeral -C "$repo" \
  --output-schema "$candidate_schema" - < "$prompt" \
  > "$run_dir/$slug.candidates.json" \
  2> "$run_dir/$slug.collect.log"
```

`$repo`, `$candidate_schema`, `$prompt`, `$run_dir`, `$slug`는 오케스트레이터가 절대경로와
검사된 slug로 채운다. 후보 JSON을 저장하라고 read-only Codex 자체에 지시하거나 `-o`에
의존하지 않는다. **바깥 오케스트레이터가 stdout을 받아 저장한다.** 스키마 불일치,
비정상 종료, 빈 stdout이면 그 수집 실행 전체를 버리고 재시도한다. 부분 JSON은 검증 단계로
넘기지 않는다.

후보 수집은 서로 저장소를 쓰지 않으므로 2026-08-14 성공 배치와 같은 최대 3개 wave로
병렬화할 수 있다. 후보 수집의 병렬성은 등재의 병렬성을 허용하지 않는다.

### 2단계 — 검증·등재

`curator`는 후보를 다음 순서로 처리한다.

1. 영구 식별자와 `(정규화 제목, 정규화 저자 집합, 연도)`로 기존 142건과 후보끼리 중복을 찾는다.
2. 존재 검증을 수행한다.
3. 존재 결과와 독립적으로 관계 및 동명이인 검증을 수행한다.
4. 둘 다 `verified`인 후보만 원문·출판사 서지 설명을 보고 tier를 사람 판단한다.
5. 주장 씨앗을 원문 위치와 대조해 본문에 쓸 수 있는지 확인한다.
6. 부족분 n과 같은 수만 승인하고, 최종 id를 부여한다.
7. 승인 행을 격리 worktree의 `sources.json`에 넣고 `wiki/sources/<id>.md`를 만든다.

이 단계는 레지스트리·원문을 읽기 위한 네트워크 접근은 허용하지만 외부 서비스에는 쓰지 않는다.
로컬 쓰기도 해당 위인의 격리 worktree와 저장소 밖 임시 감사 디렉터리로 제한한다. 후보의
`authors` 배열은 승인 때 기존 스키마의 세미콜론 구분 문자열로 직렬화한다. DOI는 기존처럼
최상위 `doi`에 정규화해 두고, ISBN·ERIC·OpenLibrary edition·OCLC는 `identifiers` 객체에도
보존해 다음 위인 트랜잭션의 중복 검사 입력으로 쓴다.

중복 키에서 저자를 빼지 않는다. DOI·ERIC·OpenLibrary edition·OCLC·ISBN 중 같은 정규화
식별자가 하나라도 있으면 같은 레코드 후보로 본다. 영구 식별자가 없을 때만 제목을 NFKC,
대소문자, 문장부호, 연속 공백 기준으로 정규화하고, **정규화한 저자 집합과 연도까지 모두
같을 때** 자동 중복 후보로 올린다. `(제목, 연도)`만 같은 서로 다른 저작은 합치지 않는다.
저자가 없거나 판본 차이가 있으면 사람이 판정한다. 같은 저작의 다른 판본은 그 판본에만
있는 주장을 쓸 때만 별도 출처로 승인한다.

새 `sources.json` 행에는 Phase 1의 `tier_review` 외에 확장 검증을 남긴다.

```json
{
  "source_review": {
    "existence": {
      "status": "verified",
      "method": "openlibrary-edition",
      "record_id": "OL...M",
      "evidence": "https://openlibrary.org/books/OL...M",
      "matched_fields": ["title", "authors", "year", "publisher"]
    },
    "relation": {
      "status": "verified",
      "pioneer": "edgar-dale",
      "kind": "authored_by",
      "person_role": "author",
      "evidence_url": "관계와 동일인을 확인한 URL",
      "locator": "title page",
      "evidence": "판본 표제지의 저자명과 도서관 전거의 동일인 식별 근거",
      "identity_signals": [
        {
          "kind": "library-authority",
          "value": "전거 id와 정규 이름",
          "evidence_url": "전거 URL"
        }
      ]
    }
  }
}
```

최종 `relation`에는 종류와 관계없이 `evidence_url`·`locator`·`evidence`가 필요하다.
`authored_by`는 `identity_signals`도 필요하고, `about`·`criticizes`는 원문에서 확인한 이름·
모형명과 그 문헌이 실제로 분석·비판한 명제를 기록한다. 링크가 열린다는 사실이나 후보 모델의
요약문만으로 이 필드를 채우지 않는다.

`sources.json`에는 승인된 `verified` 행만 들어간다. `pending_manual`과 `rejected`는 위인별
감사 기록에는 남기되 레지스트리와 승인 id 목록에는 넣지 않는다. 현재 142행을 전부
`source_review`로 소급 감사하지는 않는다. 확장 시작 시 고정한 142개 baseline id 밖의 모든
새 행에 이 객체가 있는지를 확장 검증기가 강제한다.

완료된 위인 감사 기록은
`docs/superpowers/audits/source-expansion/<slug>.json`에 커밋한다. 여기에는 시작 건수,
필요 수, 승인 id, 두 검증 축의 근거, tier 판정, 고유 주장 맵, 탈락·보류 후보와 이유를
남긴다. 작업 중 JSON과 원문 발췌는 저장소 밖의 전용 임시 디렉터리에 둔다. `raw/`의
비커밋 원칙과 저작권 경계를 유지하고, 완료 감사 기록에는 짧은 근거 설명·URL·위치만 남긴다.

### 3단계 — 본문 서술

본문 생성기에는 전체 `sources.json`을 주지 않는다. 확장 뒤 258건 전체가 보이면 승인되지
않은 실재 문헌이나 다른 위인의 출처를 가져올 수 있다. 위인별 임시 입력 디렉터리에 다음만
복사한다.

- 현재 `wiki/pioneers/<slug>.md`
- 그 파일이 이미 정의한 기존 각주
- 단계 2에서 **그 위인에게 승인된 새 id n개**의 정확한 서지, tier, 관계 근거, 주장 근거
- `CLAUDE.md`의 프론트매터·각주·confidence·개념 링크 규칙
- 쓸 수 있는 기존 개념 링크 목록

생성기는 read-only로 이 패킷을 읽고 stdout에 수정 페이지와 주장 맵을 구조화해 반환한다.
오케스트레이터만 실제 `wiki/pioneers/<slug>.md`를 쓴다. 새 id마다 주장 맵 한 행이 필요하다.

```json
{
  "source_id": "new-id",
  "section": "기억률 피라미드는 데일의 것이 아니다",
  "claim": "페이지에 들어간 정확한 한 문장 또는 목록 항목",
  "evidence_locator": "원문 쪽·절·초록 위치"
}
```

검증기는 다음을 모두 요구한다.

- 단계 2 승인 id 집합 = 새 프론트매터 id 집합 = 새 각주 정의 집합
- 승인 id 각각이 본문의 각주 참조로 적어도 한 번 사용됨
- 승인 id마다 서로 다른 새 주장 문자열과 근거 위치가 있음
- 승인 목록 밖의 새 id는 0건
- 기존 각주·본문을 근거 없이 삭제하지 않음
- 각주 서지는 `sources.json`의 제목·tier와 일치함

문장을 만들 수 없으면 출처를 억지로 등재하지 않는다. 그 후보를 `rejected`로 되돌리고 같은
위인의 새 후보를 검증한다. 서지 수를 맞추기 위해 제목·발행연도만 말하는 빈 연표 항목을
만드는 것도 허용하지 않는다. 새 주장은 핵심 명제, 모형의 조건, 적용 범위, 비판, 오용,
판본 차이, 연구 결과처럼 그 위인의 실질 질문에 답해야 한다.

## D2 — 존재 검증과 관계 검증을 별도 축으로 기록한다

후보마다 `existence.status`와 `relation.status`를 각각
`verified`·`pending_manual`·`rejected` 중 하나로 판정한다. 전체 상태는 다음처럼 계산한다.

| 존재 | 관계 | 전체 결과 |
|---|---|---|
| verified | verified이며 `authored_by`·`about`·`criticizes` | 등재 가능. 이후 tier·주장 검토 |
| 어느 한쪽이라도 rejected | 무엇이든 | rejected |
| 그 밖의 조합 | 무엇이든 | pending_manual |

`verified`는 “레지스트리에서 문자열 하나가 나왔다”가 아니다. 서지의 실재와 위인과의 관계를
서로 다른 증거로 확인했다는 뜻이다. `pending_manual`은 가짜의 완곡어가 아니라 자동·현재
경로로 판정하지 못했다는 뜻이며 등재 권한은 없다. `rejected`는 문헌 불일치, 잘못된 동명이인,
관계 없음, 일반 배경뿐임, 기존 레코드 중복처럼 탈락 이유가 확인된 상태다.

### 존재 검증 경로

레지스트리는 문헌의 실재와 서지 정체만 확인한다. tier와 관계를 정하지 않는다.

| 경로 | 주 사용처 | verified에 필요한 것 | 이 경로만으로 못 하는 것 |
|---|---|---|---|
| DOI + Crossref/DOI 해석 | 현대 저널 논문·장·도서 | DOI 정확 일치, 제목·저자·연도 대조 | 원저작/종합서 tier, 위인과의 관계 |
| OpenLibrary edition | DOI 없는 단행본의 특정 판본 | edition id와 저자·제목·출판사·연도 일치 | 그 판본의 주장 내용 |
| ERIC | 교육 보고서·논문·자료 | ED/EJ 번호와 서지 일치 | 동명이인과 본문 관계의 최종 판정 |
| 도서관 서지 레코드 | 구 단행본·희귀 판본 | LCCN/OCLC 등 안정 id와 판본 서지 일치 | 문헌이 특정 이론을 다룬다는 의미 |
| 도서관 인명 전거 | 동명이인 식별 | 전거 id, 정규 이름, 생몰연도·소속 등 일치 | 문헌 자체의 존재. 단독 존재 근거로 쓰지 않음 |
| 저널 공식 권호 목차 | DOI 없는 구 논문 | 권·호·쪽에 정확한 제목·저자 확인 | 본문이 실제로 비판하는지 |
| 출판사·대학·학회 공식 기록 | 공식 약력·부고·기관 기록 | 발행 주체와 안정 URL, 표시 제목·인물 확인 | A 승격. 기관 기록은 Phase 1 규칙상 B |
| 원문 스캔의 표제지·판권지 | 다른 레지스트리 공백의 최종 수동 경로 | 표제지·판권지에서 저자·제목·판본·발행처 확인 | 자동 검증 상태 |

Crossref 미검색은 `rejected`가 아니다. 현재 DOI는 142건 중 28건뿐이고, 1910~1950년의
8개 레코드에는 하나도 없다. 데일 1946, 손다이크 1913, 프레시 1926 같은 문헌을 Crossref
하나로 판정하면 진짜 고문헌을 체계적으로 버린다. DOI가 없으면 OpenLibrary edition,
ERIC ED/EJ, 도서관 서지, 저널 권호 목차, 표제지 순으로 보조한다. 그래도 정체를 확인하지
못하면 `pending_manual`로 두고 다른 후보를 찾는다.

DOI가 해석되더라도 후보의 제목·저자와 다른 문헌을 가리키면 존재 검증을 통과하지 않는다.
부제 누락·온라인 우선연도처럼 설명 가능한 경미한 차이는 레지스트리 값으로 정정하고
`corrections`에 남긴 뒤 관계를 다시 본다. 전혀 다른 논문을 가리키는 DOI는 `rejected`다.

### 관계 유형과 승인 근거

관계는 위인 페이지를 기준으로 하나의 주 관계를 고른다.

| `kind` | 의미 | 승인에 필요한 증거 | 할당량 포함 |
|---|---|---|---|
| `authored_by` | 위인이 저자·편집자·인터뷰이로 직접 참여 | 역할이 표시된 저자란·표제지·초록·본문과 동일인 근거 | 가능 |
| `about` | 문헌이 위인 또는 그 이론을 직접 분석·검토 | 제목·초록·본문에서 이름 또는 식별 가능한 이론을 직접 다루는 위치 | 가능 |
| `criticizes` | 위인 또는 이론을 명시적으로 비판·비교 | 비판·대조의 실제 명제와 쪽·절·초록 위치 | 가능 |
| `context_only` | 교육·심리·매체의 일반 배경일 뿐 | 직접 관계 근거 없음 | 불가. 관계 `rejected`로 처리 |

`authored_by`에는 `person_role: author | editor | interviewee`를 반드시 둔다. 편집자라는 이유로
tier A가 되지 않으며, 인터뷰이는 기사 저자와 구분한다. `about`은 참고문헌에 이름이 한 번
나오는 것만으로 통과하지 않는다. 본문이 그 사람이나 이론을 분석하는 문장과 위치가 필요하다.
`criticizes`도 “선행연구로 인용했다”가 아니라 무엇을 반박·대조했는지를 기록해야 한다.

이론 이름만 있는 경우에는 그 이론이 해당 위인에게 귀속된다는 독립 근거와 본문 위치를 함께
요구한다. “학습”, “동기”, “인지부하” 같은 일반어는 이름 없이 관계를 증명하지 못한다.
ARCS, 4C/ID처럼 식별력이 높은 모형명도 원문 위치와 공식 귀속 근거를 함께 기록한다.

### 동명이인 방어

문자열 이름 일치는 동일인 판정이 아니다. 모든 관계 후보는 문헌의 인물이 페이지 주인과
같다는 근거를 갖는다. `authored_by` 후보는 정규 이름 외에 소속, 분야, 생몰연도, 공저자,
공식 CV, ORCID, VIAF/도서관 전거 가운데 적어도 하나의 독립 식별 신호를 갖는다.
`about`·`criticizes`도 이름이 가리키는 분야·이론·소속을 대조한다.
`John Keller`·`Richard Clark`·`Allan Collins`는 관계 종류와 무관한 명시적 고위험 이름으로
두 신호를 요구하며, 둘 중 하나는 공식 소속/CV 또는 영구 인명 전거여야 한다.

예를 들어 “John Keller”라는 저자 문자열과 Crossref DOI가 모두 맞아도 교육공학자 John M.
Keller라는 소속·공저·모형 연결이 없으면 `pending_manual`이다. 다른 분야의 동명이인으로
확인되면 `rejected`다. 이름의 중간 이니셜이 없다는 사실만으로 같은 사람으로 올리거나 다른
사람으로 버리지 않는다.

## D3 — tier는 레지스트리가 아니라 사람이 근거 역할을 보고 정한다

관계가 확인된 뒤 `curator`가 Phase 1의 판정 순서를 그대로 적용한다.

1. 위인 본인이 자기 데이터·논증·이론·모형을 처음 제시한 원저작·직접 기록이면 A
2. 단행본·수록 장은 표제지, 서문, 목차, 출판사 설명, 실제 인용 위치를 보고 원저작이면 A,
   종합·편집·해설·교재·번역이면 B
3. 타인이 쓴 학술 문헌과 학회·대학 등 기관 공식 기록은 B
4. 백과사전·일반 참고 자료는 C이며 단독 근거 금지

Crossref의 `book`·`journal-article`, OpenLibrary의 edition, ERIC의 자료형은 실재와 형식을
돕지만 원저작/종합서 경계를 답하지 않는다. Phase 1에서 형식만으로 판정할 수 없던 22행은
원문·출판사 서지 설명을 직접 봐야 했다. 같은 판단을 새 116행에도 적용한다.

새 행의 `tier_review`는 다음 계약을 지킨다.

- `rule`은 `1-original-work`·`2-book-or-chapter-role`·
  `3-other-scholar-or-institution`·`4-general-reference` 중 하나
- `evidence`는 빈 문자열이 아니며 확인한 자료형 기본값 또는 서지 URL과 근거 역할을 설명
- 새 행이므로 `changed_from`을 만들지 않음
- 수집 후보의 추정 tier를 복사하지 않음
- 최종 `type`이 원저작 기본형 또는 `연구서`면 lint 규칙 10의 자료형 기본값과 일치

관계와 tier는 직교한다. 다른 위인이 쓴 원논문이 대상 위인을 비판하면 관계는
`criticizes`이고 전역 tier는 그 비판자 본인의 원저작 A일 수 있다. 페이지 주인과 저자가
다르다고 자동으로 B로 내리지 않는다. 반대로 대상 위인이 편집자로 참여한 후대 종합서는
`authored_by`여도 B일 수 있다.

## D4 — 본인 저작을 우선하되 confidence를 목표로 삼지 않는다

한 위인 안의 후보 우선순위는 다음과 같다.

1. 핵심 모형·데이터·설계 원리를 직접 제시한 위인 본인의 원저작
2. 판본 차이, 적용 조건, 한계, 오용을 직접 설명하는 본인의 회고·후속 저작
3. 위인이나 이론을 직접 검토·비판·비교한 타인의 학술 문헌
4. 실제로 비어 있는 생애·경력 사실을 받치는 대학·학회·기관 공식 기록
5. C 자료는 탐색 출발점으로만 사용. 새 116건의 할당량에는 넣지 않음

C를 할당량에서 빼는 이유는 수치만 10으로 올리는 가장 쉬운 경로를 차단하기 위해서다.
필요한 직접 근거가 있는 A·B가 없으면 그 위인은 보류한다. 기존 C는 삭제하지 않으며,
새 A·B와 병행 인용될 수 있다.

위인 처리 순서는 데일을 첫 번째로 하고, 그다음 부족분 +6 → +5 → +4 → +3 → +2 → +1,
같은 그룹에서는 slug 오름차순으로 고정한다. 데일을 먼저 두는 이유는 낮은 출처 수와 유일한
C 단독 실질 주장이 동시에 있어 설계의 “넓이가 깊이를 낳는다”는 가정을 가장 빨리 검증하기
때문이다. 데일 트랜잭션은 단순히 10건을 만드는 것뿐 아니라 기억률 피라미드 절에 직접
관계가 검증된 A 또는 B 근거를 붙여 C 단독을 해소해야 한다.

다른 페이지에서는 A 없는 33개 섹션을 작업 목록으로 사용하지 않는다. 생애 B를 A로 만들기,
`confidence: high` 수 맞추기, 모든 medium을 high로 올리기는 비목표다. 본문 작성기에도
목표 confidence를 주지 않는다. 마지막에 `sync:confidence`가 계산한 값을 받아들인다.

## D5 — 위인 한 명이 하나의 트랜잭션이다

116건을 한꺼번에 등록하거나 출처 하나마다 커밋하지 않는다. 위인 한 명의 부족분 전체를
다음 원자 단위로 묶는다.

```text
마지막 green main
  → <slug> 격리 worktree/branch
  → 후보 수집(stdout, repo 무변경)
  → 존재·관계·tier·주장 검증
  → sources.json + source 페이지 n개를 worktree에 준비
  → 승인 id n개만으로 위인 본문 작성
  → confidence 동기화 + 확장 검증 + 전체 게이트
  → 한 커밋
  → main에 순차 반영
```

한 트랜잭션이 수정할 수 있는 업무 파일은 다음뿐이다.

- `sources.json`
- 승인된 새 id의 `wiki/sources/<id>.md`
- `wiki/pioneers/<slug>.md`
- `docs/superpowers/audits/source-expansion/<slug>.json`

준비 단계에서 확장 검증 스크립트·스키마·baseline 감사 파일을 별도 green 커밋으로 먼저
세운다. 이후 위인 커밋은 위 네 범위만 수정한다. `git diff --name-only`가 허용 목록 밖 파일을
보이면 트랜잭션을 커밋하지 않는다.

위인 커밋의 종료 조건은 “일부 후보를 넣음”이 아니다. 시작 수가 4이고 부족분이 6이면 승인
6건 전부가 존재·관계 검증, tier 기록, source 페이지, 고유 주장, 프론트매터를 갖고 그 페이지가
정확히 10건이 되어야 한다. 하나라도 실패하면 5건만 커밋하지 않는다.

실패 worktree/branch는 메인에 병합하지 않고 `pending_manual` 후보와 실패 이유를 유지한다.
메인은 그대로 green이므로 다음 위인을 새 worktree에서 진행할 수 있다. 나중에 보류 위인을
재개할 때 최신 main 위로 재배치한 뒤, 이미 다른 트랜잭션에서 추가된 id와 중복을 다시 검사하고
전체 게이트를 다시 돈다. 오래된 검증 결과를 그대로 병합하지 않는다.

새 출처는 한 위인 트랜잭션이 소유한다. 두 위인을 비교하는 문헌도 이번 116건 중 하나의
소유 위인과 한 고유 주장에만 할당한다. 다른 위인 페이지로 재사용하는 확장은 31명 최소 10건을
모두 닫은 뒤 별도 작업으로 다룬다. 그래야 116 부족분과 116 새 행·116 새 주장의 대응이 깨지지
않고 서로 다른 위인 브랜치가 같은 source 페이지를 동시에 만들지 않는다.

## 검증 설계

### 확장 전용 검증기

준비 커밋에서 `npm run verify:source-expansion`을 추가한다. baseline 감사 파일에는 현재
142개 id와 기준 커밋을 고정한다. 위인별 모드와 전체 모드가 다음을 검사한다.

- baseline 밖의 모든 `sources.json` 행이 완료 감사 기록에 정확히 한 번 나타남
- 새 행의 `source_review.existence.status`와 `relation.status`가 모두 `verified`
- 관계 kind가 `authored_by`·`about`·`criticizes` 중 하나이며 `context_only`가 아님
- 고위험 동명이인은 요구한 두 식별 신호가 있음
- 모든 새 행에 lint 규칙 10을 만족하는 `tier_review`가 있음
- DOI·ERIC·OpenLibrary edition·OCLC·ISBN 중복과 `(제목, 저자, 연도)` 중복이 없음
- 승인 id, 새 각주 정의, 새 프론트매터 id, 주장 맵이 정확히 일치
- 주장 맵의 문장이 실제 대상 섹션에 있고 같은 id 각주를 참조함
- 한 위인의 새 주장 문자열이 서로 다름
- 대상 위인의 최종 `sources` 길이가 10이며 정확히 부족분만 추가됨
- source 페이지가 존재하고 해당 위인 각주 링크를 통해 index에서 도달 가능함
- 전체 모드에서 새 id 116개, `sources.json` 258개, 36명 모두 최소 10개

존재·관계의 자연어 근거가 참인지는 스크립트가 자동 판결할 수 없다. 검증기는 빈 근거,
허용하지 않은 상태, 잘못된 id 연결, 동명이인 신호 누락을 잡고, `curator`가 URL·원문 위치를
직접 대조해 의미를 서명한다. 모델의 `verified` 문자열만으로 통과시키지 않는다.

### 기존 명령과 역할

| 명령 | 이 확장에서 잡는 것 | 잡지 못하는 것 |
|---|---|---|
| `npm run verify:source-expansion -- --pioneer <slug>` | 위인 트랜잭션의 승인·관계·중복·주장 1:1·10건 완료·허용 파일 계약 | 근거 URL의 자연어가 실제 주장을 함의하는지 |
| `npm run lint:strict` | 규칙 1~12: 프론트매터/각주 집합, 출처 id, source 페이지 도달성, confidence, 서지 제목, `tier_review`, 각주와 source 페이지 tier | 문헌 실재, 동명이인, 관계 의미 |
| `npm run sync:confidence` | 최종 각주·tier로 파생 confidence 갱신 | 출처 선택과 tier 판정의 정당성 |
| `npm test` | 확장 검증기·중복 정규화·상태 계산과 기존 171개 회귀 | 실제 116건 원문 판정 |
| `npm run lint:answers` | 기존 답변의 위조급 회귀와 tier 표기 | 새 위인 본문. answers는 이번에 쓰지 않음 |
| `npm run audit:citation-years` | 새 문장 때문에 생긴 오래된 출처/무연도 후보 | 후보의 정오. 계속 비차단 |
| `npm run build` | 최종 사이트 링크·렌더·source 역참조 | 관계와 주장 의미 |
| `git diff --check` | 공백 오류 | 데이터 의미 |

`sync:confidence`는 검사가 아니라 파생값 쓰기다. 본문 완료 뒤 한 번 실행하고, 다시
`npm run sync:confidence -- --dry`를 실행해 갱신·제거·건너뜀이 모두 0인지 확인한 뒤 strict
lint를 돈다.

`audit:citation-years`는 Phase 1과 같이 비차단으로 유지한다. 다만 위인별 감사 기록에는
그 트랜잭션이 새로 만든 연도 후보와 비교 불가 항목의 판정을 반드시 넣는다. Phase 1의 이미
판정된 164쌍을 매 위인마다 다시 판단하지 않고, 기준 감사 key와 비교해 새로 생기거나 문장이
바뀐 key만 검토한다. 새 key가 미판정이면 위인 트랜잭션은 확장 검증을 통과하지 못한다.

### Phase 1 감시 조건의 재검사

1. `KNOWN-ISSUES` 5번 — 전체 완료 뒤 C 단독 섹션을 다시 센다. 데일의 대상 절은 직접
   관계가 검증된 A/B와 병행돼야 한다. 다른 C 단독을 새로 만들면 실패다.
2. `KNOWN-ISSUES` 6번 — 새 tier A의 원저작자가 페이지 주인과 다른 사례를 전수 출력한다.
   `당대의 비판`·`대립축`에서는 올바른 `criticizes` 근거일 수 있다. 그 밖의 생애·대표 저작·
   핵심 명제를 대신 받치면 사람이 관계와 각주 범위를 다시 판정한다. 자동 B 강등은 하지 않는다.
3. `KNOWN-ISSUES` 7번 — 새·변경 문장의 연도 후보만 사람 판정한다. 후보가 존재한다는 이유로
   strict lint를 실패시키거나 allowlist로 숨기지 않는다.

위인 한 명의 커밋 직전 순서는 고정한다.

```text
verify:source-expansion --pioneer <slug>
→ sync:confidence
→ sync:confidence --dry (0/0/0)
→ lint:strict
→ npm test
→ lint:answers (exit 0, 위조급 0)
→ audit:citation-years 새 key 판정 완료
→ npm run build
→ git diff --check
→ 허용 파일 목록 확인
→ commit
```

전체 31명 완료 뒤에는 전체 모드의 116/258/36명 최소 10 검사를 추가해 같은 게이트를 한 번
더 실행한다.

## 실패 처리

### 레지스트리에서 찾지 못함

즉시 탈락시키지 않는다. DOI가 없으면 OpenLibrary edition, ERIC, 도서관 서지, 저널 권호
목차, 표제지·판권지로 이동한다. 어느 경로도 정체를 확정하지 못하면 `pending_manual`이고
할당량에는 들어가지 않는다. 더 강한 메타데이터가 생기면 같은 candidate key로 재개한다.

### 실재하지만 관계가 약함

일반 교육심리 배경, 참고문헌의 이름 한 번, 이론과 무관한 동명이인은 `rejected`다.
`sources.json`에 넣지 않고 감사 기록에 이유를 남겨 다음 수집이 같은 문헌을 다시 제안하지
않게 한다. 실재한다는 사실은 관계 탈락을 뒤집지 않는다.

### 검증 후보가 부족함

그 위인 worktree는 커밋하지 않고 다음 위인으로 간다. 추가 수집은 부족 수 기준으로 반복하고,
본인 저작의 판본·후속 논문, 직접 검토·비판 문헌, 공식 기관 기록 순으로 경로를 넓힌다.
그래도 10건에 못 미치면 그 위인은 보류 목록에 정확한 부족 수와 `pending_manual`·`rejected`
이유를 남긴다. C나 `context_only`로 수를 채우거나 9건을 완료라고 선언하지 않는다. 한 명이라도
10건 미만이면 Phase 2 전체 목표는 미완료다.

### 본문 서술이나 게이트 실패

출처는 맞지만 고유 주장을 만들 수 없으면 그 출처 승인을 취소하고 교체한다. source 페이지만,
프론트매터만, 본문 각주만 남은 부분 상태는 커밋하지 않는다. 격리 branch에서 원인을 고쳐
전 게이트를 다시 돌리거나 branch를 보류한다. 다음 위인의 main 기준선은 계속 green이다.

### 중단과 재개

완료 커밋은 위인 단위라 중간에 멈춰도 main에는 완결된 위인만 남는다. 보류 branch를 재개할
때는 최신 baseline 이후 추가된 영구 식별자와 `(제목, 저자, 연도)` 중복을 다시 계산하고,
승인 패킷을 새로 생성한다. 이전 본문 생성기가 보았던 승인 목록을 재사용하지 않는다.

## 채택하지 않는 대안

### 레지스트리 메타데이터에서 tier를 유도한다

폐기한다. Crossref의 `book`·`journal-article`은 형식이지 원저작/종합·편집·교재의 근거 역할이
아니다. Phase 1의 22행 의미 판정에서 원문·출판사 설명이 실제로 필요했다. 레지스트리는
존재에만 사용하고 tier는 사람이 판정한다.

### 존재 검증만 통과하면 등재한다

이 설계가 막으려는 세탁 경로다. 실재하는 아무 논문이나 교육공학 위인의 B 출처로 바꿀 수
있다. 관계 검증과 동명이인 검증이 별도 `verified`가 아니면 등재하지 않는다.

### 이름 문자열 또는 성씨로 동일인을 판정한다

John Keller·Richard Clark·Allan Collins의 동명이인 위험을 막지 못한다. 하이픈 성씨를
기계 추출하다 오탐을 낸 Phase 1 시뮬레이션의 교훈도 거스른다. 공식 소속·CV·전거와 복수
식별 신호를 사용한다.

### 중복 키를 `(제목, 연도)`로 둔다

저자가 다른 동명 저작을 합친다. 영구 식별자를 우선하고 fallback에도 저자 집합을 반드시 넣는다.

### Crossref 미검색을 가짜로 판정한다

현재 구 문헌과 DOI 실측이 반례다. 미검색은 `pending_manual`이고 보조 레지스트리와 원문
판본 확인으로 이동한다.

### 후보 JSON을 read-only Codex가 파일로 쓰게 한다

`-s read-only`의 권한과 모순돼 실패한다. 반대로 `-s`를 생략하면 전역
`danger-full-access`가 적용된다. read-only 수집기의 stdout을 오케스트레이터가 저장하는
경계를 사용한다.

### 본문 생성기에 전체 `sources.json`을 준다

확장 완료 시 258건 전체가 인용 후보가 되어 위인별 관계 승인이 무력화된다. 위인별 승인 id와
근거 패킷만 주고, 승인 목록 밖 새 id를 기계적으로 거부한다.

### 116건을 한 배치 커밋으로 넣는다

한 실패가 전체를 빨갛게 만들고 중단 시 부분 상태를 남긴다. 출처 하나씩 커밋하면 반대로
위인 페이지가 10건이 되기 전 불완전 상태가 main에 쌓인다. 위인 한 명이 의미와 게이트가
닫히는 최소 트랜잭션이다.

### A 없는 33개 섹션을 모두 없앤다

생애·경력의 올바른 근거가 기관 B인 경우까지 A를 찾게 해 지표가 내용을 움직인다. 본인
원저작 우선은 실질 주장에 적용하고 confidence 분포 자체는 목표로 삼지 않는다.

### `context_only`와 새 C를 할당량에 넣는다

관계가 없는 문헌이나 일반 참고 자료로 숫자 10을 만드는 경로다. 탐색에는 쓸 수 있지만 새
116건의 승인 출처가 될 수 없다.

## 범위 밖

- 실제 116개 후보 선정·원문 판정·등재·본문 작성. 이 문서는 구현 전 설계다
- 기존 142행의 관계를 전면 소급 감사하는 일. 새 116행은 baseline 밖 행으로 강제한다
- 이미 10건 이상인 블룸·메릴·메이어·가녜·파퍼트를 더 늘리는 일
- 새 위인, 새 debate, 새 concept 페이지 생성. 필요한 새 개념은 `proposed_concepts`로만 제안
- 기존 concept·debate·answer 본문 보강
- 생애 B를 A로 만들거나 모든 페이지를 `confidence: high`로 만드는 일
- confidence 공식을 저자 상대적으로 바꾸거나 타인의 A를 자동 B로 강등하는 일
- 모든 자연어 주장과 문헌의 함의를 자동 판정하는 범용 검증기
- Phase 1의 164개 연도 판정을 새 확장 때마다 재수행하는 일
- 봇, 라우터, 사이트 기능과 출력 형식 변경

## 완료 조건

- baseline 142건 밖에 새 고유 출처 116건이 있고 `sources.json`은 정확히 258건이다.
- 36명 모두 프론트매터 `sources`가 최소 10건이며 31명 트랜잭션이 각각 한 green 커밋이다.
- 새 116행 전부에 `source_review`의 존재·관계 `verified`와 Phase 1 형식의 `tier_review`가 있다.
- 새 116행 중 `context_only`와 C는 0건이고, 동명이인 고위험 후보는 복수 식별 근거가 있다.
- 새 source 페이지 116개가 있고 위인 각주 링크를 통해 도달 가능하다.
- 새 id 116개 각각에 서로 다른 근거 주장과 원문 위치가 감사 기록에 있으며 본문에서 같은
