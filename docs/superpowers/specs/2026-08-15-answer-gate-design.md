# 답변 게이트 — 설계 명세

**날짜** 2026-08-15
**상태** 승인됨

## 문제

`lint`의 8규칙은 `wiki/`의 정적 코퍼스만 검사한다. 그런데 이 시스템의 산출물은 `/ask`·`/debate`가
런타임에 생성한 **답변**이고, 답변은 저장되지도 검사되지도 않는다.

`[근거]`·`[적용]`·`[근거없음]` 세 마커는 `scripts/` 전체에서 `gen-agents.mjs`에만 등장한다 —
에이전트 프롬프트를 찍어낼 때뿐이다. `lint-wiki.mjs`는 이 문자열을 모른다.

프로젝트의 주장은 "모든 말에 근거를 인용한다"인데, 근거 DB만 감사받고 그 DB로 한 말은
감사받지 않는다. 이 비대칭을 없앤다.

## 무엇을 만드는가

답변을 파일로 저장하고 11개 규칙으로 검사한다. 검사는 두 지점에서 돈다.

1. **런타임** — `/ask`·`/debate`가 답변마다 검사하고 결과를 출력에 붙인다
2. **커밋 게이트** — `npm run lint:answers`가 `answers/` 전수를 재검사하고 CI 게이트 4로 들어간다

런타임 검사는 오케스트레이터의 준수에 의존한다. 커밋 게이트가 그 약점을 막는다 —
런타임에 검사를 건너뛰더라도 **검사를 통과하지 않은 답변은 저장소에 들어올 수 없다.**

## 이 프로젝트에서만 가능한 검사

설계 결정 ②(위인 격리) 때문에 **각 위인이 인용해도 되는 출처 집합이 자기 페이지 프론트매터
`sources`로 확정**되어 있다. 가녜의 답변에 `papert-1980`이 나오면 그건 위조다.
일반 RAG 시스템에서는 성립하지 않는 검사이며, 이 게이트의 핵심이다(규칙 3).

## 답변 파일 포맷

오케스트레이터와 검사기 사이의 유일한 인터페이스다.

```markdown
---
type: answer
command: ask                    # ask | debate
question: "LMS를 새로 설계한다면 무엇부터 보나"
asked: 2026-08-15
speakers: [robert-gagne, richard-mayer]
---

## robert-gagne

[근거] 학습 결과의 종류에 따라 필요한 조건이 달라진다.[^gagne-1965]

[^gagne-1965]: Robert M. Gagné. (1965). The Conditions of Learning.
    Holt, Rinehart and Winston. — tier A · [[sources/gagne-1965]]

## richard-mayer

[적용] 이중 채널 원리에서 추론하면 …[^mayer-2009]

## _orchestrator

이 둘은 설계의 출발점에서 갈린다.
```

- `## <slug>`가 화자 구분자다. `wiki-parse.mjs`의 `sections()`가 이미 `## `를 자르므로 재사용한다
- `/debate`는 같은 slug이 라운드마다 반복 등장한다. 문서 순서 = 라운드 순서
- `_orchestrator`는 예약 화자다. 이 섹션에는 각주를 쓸 수 없다 — 사회자가 각주를 달면
  그건 위인 발언의 합성이다. 커맨드 문서의 "요약하지 않는다" 금지가 처음으로 기계 검사를 받는다
- 답변 본문은 원문 그대로다. 저장 과정에서 요약하지 않는다

**위치는 `wiki/` 밖이다.** `answers/`에 둔다. `wiki/` 안에 두면 `lintWiki`가 답변까지 검사해
규칙 1(`type`이 `PAGE_TYPES`에 없음)과 규칙 7(색인에서 도달 불가)이 전부 깨진다.

파일명은 `answers/YYYY-MM-DD-<질문슬러그>.md`. 같은 날 같은 슬러그가 겹치면 `-2`를 붙인다.

## 검사 규칙 11개

`lint-wiki.mjs`의 `SOFT_RULES` 관용구를 따라 심각도를 둘로 나눈다.

### 위조급 — 재호출 1회

| # | 규칙 | 뜻 |
|---|---|---|
| 1 | 각주 참조 `[^id]`에 정의가 있다 | 근거 없이 인용 표시만 달았다 |
| 2 | 각주 id가 `sources.json`에 실재한다 | **출처를 지어냈다** |
| 3 | 각주 id가 화자 페이지의 프론트매터 `sources` 안에 있다 | **인용 범위를 벗어났다** |
| 4 | 각주 정의의 `tier X` 표기가 `sources.json`의 tier와 일치한다 | 티어를 위조했다 |
| 5 | 화자가 실재 pioneer slug이거나 `_orchestrator`다 | 귀속이 불가능하다 |
| 6 | 프론트매터 `speakers` ≡ 본문 화자 집합(`_orchestrator` 제외) | 화자 목록을 조작했다 |
| 7 | `_orchestrator` 섹션에 각주가 없다 | 사회자가 위인 발언을 합성했다 |

### 형식급 — 기록만

| # | 규칙 | 뜻 |
|---|---|---|
| 8 | 각주 정의가 `— tier <A\|B\|C> · [[sources/<id>]]`로 끝난다 | 각주 형식 이탈 |
| 9 | 주장 문단이 세 마커 중 하나로 시작한다 | 마커 누락 |
| 10 | `[근거]` 문단에 각주 참조가 있다 | 근거 없는 `[근거]` |
| 11 | `[근거없음]` 문단에 각주 참조가 없다 | 마커와 내용의 모순 |

### 지표 (위반이 아니다)

마커 분포 `[근거]`/`[적용]`/`[근거없음]` 개수와 `[적용]` 비율을 함께 낸다.
질문이 대부분 현대 기술이라 `[적용]`이 다수인 것은 정상이며, 이 비율은 판정이 아니라 관측이다.

### 문단의 정의와 검사하지 않는 것

규칙 9~11의 "문단"은 `stripFootnoteDefs()` 이후 빈 줄로 나눈 블록이다.
**위인 섹션에만 적용한다** — 마커는 위인 발언의 규칙이므로 `_orchestrator` 섹션은 대상이 아니다.
다음은 마커 검사에서 **제외한다** — 인용문(`>`), 목록(`-`·`*`·`1.`), 표(`|`), `NEEDS_CLARIFICATION` 줄.

제외에는 구멍이 있다. 위인이 주장을 목록으로 늘어놓으면 마커 없이 통과한다.
오탐을 줄이려고 감수한 것이며, 규칙 9~11이 형식급인 이유이기도 하다.
`lint`가 귀속 정확성을 못 잡는다고 README에 적어둔 것과 같은 종류의 공개다.

**이 게이트도 귀속 정확성은 못 잡는다.** 규칙 3이 "가녜가 인용해도 되는 출처"까지는 확인하지만,
"이 각주가 이 문장의 근거가 맞는가"는 여전히 사람이 봐야 한다.

## 데이터 흐름

### 런타임 (`/ask`)

1. `router`가 위인 선정 → 위인 병렬 호출 → 답변 수집
2. 오케스트레이터가 `answers/<파일>.md`를 쓴다. 답변 원문 그대로
3. `node scripts/check-answer.mjs answers/<파일>.md` 실행
4. **위조급 위반이 있으면** 해당 위인만 위반 내역과 함께 1회 재호출 → 파일 갱신 → 재검사
5. 재시도 후에도 위반이면 위반을 명시한 채 출력한다. 감추지 않는다
6. 형식급 위반은 기록만 하고 답변은 그대로 출력한다
7. 검사 요약을 답변 아래에 붙인다

`/debate`도 같다. 재호출 대상은 해당 라운드의 그 위인 발언이다.

### 커밋 게이트

`npm run lint:answers` → `answers/*.md` 전수 검사.
**위조급이 1건이라도 있으면 exit 1**, 형식급은 경고로 출력하고 exit 0.
`lint-wiki.mjs`가 규칙 6·7을 기본 모드에서 경고로 낮추는 것과 같은 구조다.

CI `pages.yml`에 게이트 4로 추가한다. 게이트 1(`lint:strict`) 다음이다.

### 저장된 검사 결과는 신뢰하지 않는다

`check-answer.mjs --write`는 검사 결과를 프론트매터 `check:` 블록에 기록한다.

```yaml
check:
  status: pass          # pass | violations
  forge: 0
  form: 3
  markers: { 근거: 4, 적용: 3, 근거없음: 1 }
```

이건 사람이 읽기 위한 편의 기록이다. **`lint:answers`는 이 블록을 무시하고 본문에서 다시
계산한다.** 기록을 위조해도 게이트는 속지 않는다.

## 에러 처리

| 상황 | 처리 |
|---|---|
| `answers/` 디렉터리 없음 | 검사 0건, 통과. 신규 클론에서 CI가 죽지 않는다 |
| `answers/`에 `type: answer`가 아닌 파일 | 건너뛴다. `answers/README.md`가 여기 해당 |
| 프론트매터 YAML 파싱 실패 | 즉시 오류, exit 1 |
| `sources.json` 로드 실패 | 즉시 오류, exit 1 |
| 화자 slug이 `wiki/pioneers/`에 없음 | 규칙 5 위조급 |
| 본문에 `## ` 섹션이 하나도 없음 | 규칙 6 위조급 (화자 귀속 불가) |

## 인터페이스

```js
// scripts/check-answer.mjs
export function loadAnswerContext({ wikiDir, sourcesPath })
// → { sourceById: Map, pioneerSources: Map<slug, Set<id>> }

export function checkAnswer({ file, wikiDir, sourcesPath, ctx })
// → { findings: [{ rule, severity, speaker, message }], markers: {…} }
//   severity: "forge" | "form"
```

파일을 읽되 쓰지 않는다. `--write`와 출력 서식은 CLI 계층이 맡는다.
컨텍스트 로딩을 분리한 이유는 `lint-answers.mjs`가 위키와 `sources.json`을 파일마다
다시 읽지 않게 하기 위해서다. `ctx`를 넘기지 않으면 내부에서 한 번 로드한다.

## 테스트

`test/check-answer.test.mjs`. `test/helpers.mjs`에 `makeAnswers()`를 추가해
`makeWiki()`와 같은 방식으로 임시 답변 디렉터리를 만든다.

규칙 11개마다 위반 케이스 1개씩, 그리고 전부 통과하는 정상 케이스 1개.
`_orchestrator` 각주 금지(규칙 7)와 인용 범위(규칙 3)는 이 설계의 핵심이므로
경계 사례를 추가로 둔다 — 다른 위인의 출처, 존재하지 않는 slug, 라운드 반복 화자.

## 범위 밖

- 답변의 귀속 정확성 판정 — 기계로 못 한다. `/lint`의 표본 검토가 계속 담당한다
- 배치 감사 하네스(고정 질문셋 회귀 측정) — 검사 코어가 순수 함수라 나중에 얹을 수 있다.
  지금은 만들지 않는다
- 런타임 우회 자체의 차단 — 훅 방식은 검증 장치를 저장소 밖으로 내보내므로 채택하지 않았다.
  커밋 게이트가 사후에 반드시 잡는다
