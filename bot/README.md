# 디스코드 봇

에듀테크 오라클의 대화 프론트엔드. 설계 근거는
[`docs/superpowers/specs/2026-08-15-discord-bot-design.md`](../docs/superpowers/specs/2026-08-15-discord-bot-design.md)가 정본이다.

디스코드 슬래시 커맨드를 받아 저장소 안에서 **헤드리스 Claude Code**(`claude -p`)를 돌린다.
그래서 `.claude/commands/`, 위인 에이전트 36개, 위키 접근, 답변 게이트가 전부 그대로 작동한다.
오케스트레이터를 다시 쓴 곳은 없다.

## 구조

| 파일 | 역할 | 순수한가 |
|---|---|---|
| `render.mjs` | 답변 마크다운 → 웹훅 페이로드 | **순수** — 파일시스템도 디스코드도 모른다 |
| `gate.mjs` | 발언 한 건을 답변 게이트에 통과시킨다 | 임시 파일 하나만 |
| `single-instance.mjs` | 봇이 한 대만 뜨게 한다 | 포트만 |
| `run-claude.mjs` | `claude -p` 실행 · 결과 해석 · 답변 파일 찾기 | 프로세스와 `answers/`만 |
| `index.mjs` | 디스코드 배선 · 커맨드 · 버튼 · 락 | 아니오 |

의존 방향은 **bot → scripts 한 쪽뿐**이다. 위키 도구와 사이트 빌드는 봇의 존재를 모르고,
`npm install` 없이도 그대로 돈다. 루트의 "런타임 의존성 0"이 유지되는 이유다.

화자 경계(`speakerSections`)는 답변 게이트에서 그대로 가져다 쓴다. 복사하면 언젠가
갈라지고, 갈라지는 순간 봇이 **다른 위인의 얼굴로** 발언을 게시한다.

## 준비

```bash
cd bot && npm install
cp config.example.json config.json   # 값을 채운다. config.json은 커밋되지 않는다
```

| 키 | 값 |
|---|---|
| `repo` | 저장소 절대 경로. 여기서 `claude -p`가 돈다 |
| `token` | 개발자 포털 > Bot > Reset Token |
| `guildId` · `ownerId` | 서버·본인 우클릭 > ID 복사 (설정 > 고급 > 개발자 모드) |
| `webhookUrl` | 채널 설정 > 연동 > 웹후크 |
| `baseUrl` | 배포된 사이트 주소. 각주가 이 밑의 출처 페이지로 걸린다 |
| `timeoutMs` · `debateAutoMs` · `progressMs` | 한 실행의 제한 시간 · 다음 라운드로 넘어가기까지의 틈 · 진행 표시 갱신 주기 |
| `guardPort` | 단일 인스턴스 가드가 잡는 루프백 포트. 기본 47821 |
| `speakers` | 위인별 덮어쓰기. 이름도 아바타도 자동이라 보통 비워 둔다 |

이름과 아바타는 위키에서 자동으로 온다. `speakers`는 덮어쓸 때만 쓴다.

아바타는 `python3 scripts/gen-avatars.py`가 만든 이니셜 이미지(`web/assets/avatars/`)이며
사이트와 함께 배포된다. **아바타를 바꾸면 푸시해서 배포해야 디스코드가 가져간다.**

손으로 채울 값은 **`token` 하나뿐이다.** 나머지 셋은 토큰으로 API에 물어보면 나온다.

1. 개발자 포털에서 애플리케이션을 만들고 **Bot > Reset Token**으로 토큰을 받아 넣는다
2. **Installation**에서 **Guild Install**을 켠다. 이게 꺼져 있으면 초대 링크가
   "지원되지 않는 설치 유형"으로 거부된다
3. 초대 링크로 서버에 넣는다. `client_id`는 토큰 첫 조각을 base64 해독하면 나온다
4. `guildId`는 `GET /users/@me/guilds`, `ownerId`는 `GET /guilds/{id}`의 `owner_id`,
   `webhookUrl`은 `POST /channels/{id}/webhooks`로 봇이 직접 만든다

값을 손으로 나르는 단계는 오타가 나고 어디서 틀렸는지 보이지 않는다. API로 얻으면
"토큰이 유효한가 · 초대가 끝났는가"까지 같이 확인된다.

```bash
npm start
```

## 알아 둘 것

**출력 경로가 둘이다.** 위인 발언은 웹훅으로 나간다 — 메시지마다 이름과 아바타를 갈아
끼울 수 있는 유일한 방법이다. 버튼이 달린 조작 메시지는 봇 자신이 보낸다 — 채널 웹훅은
애플리케이션 소유가 아니라 components가 거부된다.

**인터랙션 토큰에 최종 출력을 걸지 않는다.** 3초 안에 "시작했다"만 답하고 나머지는 전부
웹훅으로 보낸다. 지연 응답은 15분에 만료되는데 `/debate` 3라운드는 그것을 넘길 수 있다.

**권한 모드는 `acceptEdits`다.** `dontAsk`는 Bash를 통과시키고 **Write를 거부한다**(실측).
그대로 뒀으면 봇이 답변 파일을 한 건도 저장하지 못했다.

**`/debate`는 알아서 3라운드까지 간다.** 버튼은 그 흐름에 끼어드는 수단이다 — 기다리기
싫으면 "지금 진행", 여기서 멈추려면 "종료". 버튼과 타이머는 같은 함수로 들어가 락도 같이 쓴다.

**답변은 커밋만 하고 푸시하지 않는다.** 게이트는 다음에 사람이 푸시할 때 CI가 잡는다.

**락은 메모리에만 둔다.** 파일 락은 봇이 죽으면 남아서 이후 모든 요청을 영원히 거절한다.
다만 메모리 락이 지키는 범위는 **프로세스 하나뿐이다** — 인스턴스가 하나임은
`single-instance.mjs`가 기동 시점에 루프백 포트를 잡아 보장한다. 포트를 고른 이유도 같다:
프로세스가 죽으면 OS가 회수하므로 유령 락이 남지 않는다.

**봇을 띄울 때 stderr를 함께 담아라** — `node bot/index.mjs >> bot/bot.log 2>&1`.
`console.error`가 갈 곳이 없으면 오류가 났다는 사실만 채널에 남고 원인은 사라진다.

## 검사

```bash
npm test          # bot/ 안에서
npm run test:bot  # 루트에서
```

`render.mjs`는 실제 답변 파일(`answers/2026-08-15-what-is-learning.md`)로 회귀 검사한다.
`run-claude.mjs`는 가짜 `claude` 실행 파일을 세워 실패·시간초과 경로까지 검사한다.

## 첫 실전 실행 결과 (2026-08-15)

`/ask 학습이란 무엇일까?` 한 번을 돌렸다. **약 7분** 걸렸고 메시지 11개가 나갔다.

| 항목 | 결과 |
|---|---|
| 한글 옵션 이름(`질문`) 등록 | ✓ 디스코드 API가 받았다 |
| 위인별 이름으로 게시 | ✓ 존 듀이 · 에드워드 손다이크 · 진 레이브 · 사회자 |
| 1,900자 분할 | ✓ 화자당 2~3개 |
| 웹훅 연속 게시 | ✓ 9건, 레이트리밋 안 걸림 |
| 마스크 링크 `[A1](url)` | ✓ 링크로 렌더된다 |
| 커밋만 하고 푸시 안 함 | ✓ |

게이트가 실전에서 **위조급 5건**을 잡았다. 오케스트레이터가 각주 id에 화자별 접두를
붙여(`thorndike-1913` → `t-thorndike-1913`) `sources.json`에 없는 출처가 됐다.
`/ask` 절차 7번이 해당 위인을 1회 재호출했고 최종 위조급 0으로 끝났다.
7분 중 상당 부분이 이 재시도다.

## `/debate` 실전 실행 결과 (2026-08-16)

`/debate 매체 자체가 학습 효과를 만드는가?`를 3라운드까지 돌렸다. 라운드 2는 90초 자동
진행으로, 라운드 3은 버튼으로 넘겨 **두 진입 경로를 한 번에** 태웠다.

| 미검증이었던 것 | 결과 |
|---|---|
| 라운드 제어 주입이 라운드 1에서 멈추는가 | ✓ 참가자 4명이 각 1회씩. 반박·정리 혼입 없음 |
| `--resume`이 같은 파일에 이어 쓰는가 | ✓ 커밋 3건에 답변 파일 1개(46KB). 새 파일 안 생김 |
| 라운드 3이 앞 라운드를 기억하는가 | ✓ 코즈마의 라운드 2 인정 발언을 직접 지목 |
| 자동 진행(타이머) · 버튼 경로 | ✓ 둘 다 `advance()`로 들어가 정상 진행 |

라운드별 커밋 시각은 07:01 · 07:15 · 07:18이다(라운드 1의 시작 시각은 기록되지 않았다).
라운드 2의 12분에는 자동 진행 대기 90초가 포함된다. 참가자는 라우터가 대립축
`clark-kozma`에서 시작해 **데일·메이어까지 4명**으로 넓혔다. 최종 위조급 0 · 형식급 10.
게이트가 라운드 1에서 메이어를 1건 보류했고, 재호출로 고쳐진 판이 정산에서 올라갔다.

### 이 실행에서 드러난 것

**봇이 두 대 떠 있었다.** 같은 토큰의 게이트웨이 연결이 둘이면 디스코드는 인터랙션을
**양쪽 모두**에 배달하고, `interaction.reply()`는 하나만 성공한다. 진 쪽이 던진 예외가
최상위 catch에 잡혀 채널에 "봇에서 오류가 났다"로 나갔다 — 진 쪽은 `reply()`에서 죽어
`runAndPost`까지 가지 못하므로 **오류 메시지만 뜨고 결과는 멀쩡한** 증상이 된다.
`single-instance.mjs`가 이 상황을 기동 시점에 막는다.

**아바타가 첫 메시지에서만 비었다.** 코드 원인은 아니다 — `speakers`는 기동 시 한 번만
계산되므로 한 실행 안에서 같은 위인의 `avatar_url`은 바이트까지 동일하고, 배포본도
로컬과 일치한다(200 · 같은 크기). 디스코드가 **처음 보는 URL을 서버 측에서 가져오는 동안**
기본 아이콘을 렌더한 것으로 본다. 이미지가 바뀔 때마다 `?v=` 해시가 새 URL을 만드니
**이미지 교체 후 첫 메시지 1회**만 발생한다. 캐시 무효화를 없애면 더 나쁜 쪽(옛 이미지
영구 고착)으로 돌아간다.

### 아직 모르는 것

**라운드 2에서 `게시`/`보류` 로그가 한 줄도 찍히지 않았다.** 라운드 3은 `_orchestrator`
섹션뿐이라 위인 호출이 없는 것이 정상이다. 그러나 라운드 2는 위인 발언 4건이 파일에
들어갔는데 스트림 로그가 없다. `makeSpeakerWatcher`는 최상위 `Agent` 호출에서만 발화하므로,
resume한 오케스트레이터가 위인 서브에이전트를 거치지 않고 **직접 반박을 썼을** 가능성이 있다
— `debate.md`는 각 위인을 순차로 호출하라고 요구한다.

봇이 두 대였지만 **로그의 귀속은 깨끗하다.** `debates` 상태는 `reply()`를 이긴 프로세스에만
생기므로 자동 진행 타이머도 버튼도 라운드 1을 처리한 그 프로세스로 들어간다. 즉 `bot.log`는
세 라운드를 전부 담고 있어야 했고, 없는 줄은 오염이 아니라 신호다.

게이트가 인용 범위를 검사해 위조급 0으로 끝났으니 각주 자체는 안전하다. 확인되지 않은 것은
**라운드 2 발언의 독립성**이다 — 위인 격리는 이 저장소가 인용 범위 검사를 신뢰할 수 있는
근거이므로 그냥 넘길 수 없다. 다음 `/debate`에서 라운드 2 동안 `bot.log`에 `게시` 줄이
찍히는지 보면 결론이 난다.
